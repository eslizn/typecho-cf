# Typecho-CF

[中文](README.md)

[![Deploy to Cloudflare](https://deploy.workers.cloudflare.com/button)](https://deploy.workers.cloudflare.com/?url=https://github.com/eslizn/typecho-cf)

A modern rewrite of [Typecho](https://typecho.org) in TypeScript, running on **Astro + Cloudflare Workers + D1**. Preserves Typecho's database schema for seamless data migration from PHP Typecho.

---

## Features

**Frontend**: Post list / category / tag / author / search archives (FTS5 full-text with automatic LIKE fallback for short terms), nested comments (Gravatar), RSS 2.0 / Atom 1.0 / RSS 1.0, password-protected posts, responsive default theme

**Admin Dashboard**: Post & page editor, comment moderation, media manager (R2 drag-and-drop upload), user management (5 roles), theme switcher, plugin manager (enable/disable/configure), task Queue observability, site settings, installation wizard

**System**: Theme system (npm package distribution), lazily loaded plugin system with 30+ wired hooks, PHP Typecho migration tools, PBKDF2-SHA256 authentication, CSRF protection, security headers, request-body limits, and R2 upload validation

## Installation & Deployment

### One-click deploy to Cloudflare

Click the **Deploy to Cloudflare** button above. Cloudflare will copy this repository to your GitHub / GitLab account, provision and bind the D1, R2, task Queue declared in `wrangler.jsonc`, and set up [Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/) so every push to the production branch builds and deploys automatically.

This project uses Cloudflare’s recommended [`wrangler.jsonc`](https://developers.cloudflare.com/workers/wrangler/configuration/). TOML remains supported; Deploy to Cloudflare does not require JSONC. The configuration lives at the repository root, and the Queue preflight uses Wrangler’s own configuration discovery and parser.

Keep these commands in Button/Workers Builds: Build command `pnpm run build` and Production deploy command `pnpm run deploy:ci` (equivalent to `pnpm exec wrangler deploy`). Cloudflare provisions resources before the build and runs the Build command separately, so `deploy:ci` only deploys; it does not repeat the build or Queue preflight. Non-production branches should use Cloudflare's default `pnpm exec wrangler versions upload` (or the equivalent `npx wrangler versions upload`) rather than the production deploy command.

Workers Builds selects Node.js LTS from the root `.node-version`. If an existing project has a `NODE_VERSION` build variable, set it to `26` or remove that override to use the version file. This is a build setting, not a Wrangler runtime `vars` entry.

The button reads the pushed default branch on GitHub / GitLab; uncommitted or unpushed local configuration does not take effect. If the clone step reports that repository contents cannot be fetched, confirm the source repository is public and inspect the failed request's status and error response in the browser Network panel. This message alone does not establish a Wrangler format problem.

The wizard prompts for `INSTALL_TOKEN` (recommended; generate with `openssl rand -hex 32`). After deploy, open the Worker URL at `/install` to create the site and administrator; the form requires the same token when it is set. Install still works without it, but anyone who reaches `/install` first can claim the initial administrator.

Tables are created by the install wizard on first submit — you do not need a separate D1 migration step.

### Prerequisites

- Node.js **26.x LTS**; `.node-version` selects major version `26` for CI and Cloudflare Workers Builds
- [pnpm](https://pnpm.io) **12.21.0** (`npm install -g pnpm@12.21.0`; pinned by `packageManager`; CI uses the same version)
- A Cloudflare account (only required for Cloudflare deployment)

### Local development (zero to running)

```bash
git clone https://github.com/eslizn/typecho-cf.git
cd typecho-cf
pnpm install

# Optional: protect the local install window (restart dev after writing)
# cp .dev.vars.example .dev.vars
# then replace INSTALL_TOKEN with your own random string

pnpm run dev
```

1. Open http://localhost:4321 — uninstalled sites redirect to `/install`
2. Complete the install form: site title / description, admin username, password (min 12 chars), email; if `INSTALL_TOKEN` is set, enter the install token too
3. After submit, tables and the admin user are created; sign in at `/admin`

`wrangler.jsonc` in the repo only declares binding names (D1 `DB` / R2 `BUCKET` / Queue `QUEUE`), not account-specific IDs. `pnpm run dev` uses Miniflare local storage — you do not edit this file for daily development. Put secrets in `.dev.vars` (gitignored).

### Deploy to Cloudflare without a queue

Set `TYPECHO_QUEUE_MODE=no-queue` to build from a queue-free configuration derived from `wrangler.jsonc`. The build keeps D1, R2, and static assets and omits the queue bindings and task Cron. The deployment preflight skips queue lookups and creation. The site can be installed and used in this mode, and the admin dashboard reports that the queue is unavailable.

```bash
TYPECHO_QUEUE_MODE=no-queue pnpm run deploy
TYPECHO_QUEUE_MODE=no-queue pnpm run deploy:dry-run
```

For Workers Builds, first deploy the queue-free Worker from the CLI and then connect the repository. Set `TYPECHO_QUEUE_MODE=no-queue` in the Workers Builds environment and keep using `pnpm run build` and `pnpm run deploy:ci`. The same environment variable also works with `pnpm run dev`.

Switching an existing Worker to this mode clears its deployed task Cron. Manage any existing queue resource or consumer subscription in Cloudflare. [Cloudflare Cron configuration](https://developers.cloudflare.com/workers/configuration/cron-triggers/#delete-a-cron-trigger) · [Cloudflare consumer management](https://developers.cloudflare.com/workers/wrangler/commands/queues/#queues-consumer-worker-remove)

### Deploy to Cloudflare from the CLI

You do not need to run `d1 create` or paste a `database_id`. Wrangler provisions D1 (`typecho-cf-db`) and R2 (`typecho-cf-uploads`) from the binding names and stores the link on your Cloudflare account.

```bash
pnpm exec wrangler login
pnpm exec wrangler secret put INSTALL_TOKEN   # recommended; without it, anyone who reaches /install first can become admin
pnpm run deploy
```

The local `pnpm run deploy` command runs `node scripts/ensure-queues.mjs`, `pnpm run build`, and `pnpm exec wrangler deploy` in sequence. The Queue preflight idempotently confirms the task Queue declared by the current Wrangler configuration. The Button/Workers Builds path relies on Cloudflare's resource provisioning and separate Build command, with `pnpm run deploy:ci` as the production deploy command. To validate the build and deploy configuration only, run `pnpm run deploy:dry-run`; it builds and runs `wrangler deploy --dry-run` without creating Queues. `pnpm run deploy` uses the default Wrangler configuration; pass `--env`, `--config`, or `--cwd` to `node scripts/ensure-queues.mjs` and `pnpm exec wrangler deploy` separately when needed, because chained scripts only forward arguments to the last command. Visit the Worker URL → `/install` → submit site + admin details (and `INSTALL_TOKEN`) → sign in at `/admin`.

If you deploy multiple instances in one Cloudflare account, manually change the producer `queue` and consumer `queue` in `wrangler.jsonc` to a unique task Queue name and keep both aligned; then set the same name under **Plugins → Queue → Settings** (it is used by the admin page and for configuration-drift warnings, and a mismatch does not drop tasks). Local `pnpm run deploy`, Workers Builds `pnpm run deploy:ci`, and the Button all use the updated Wrangler configuration.

New sites enable the Queue plugin (Cloudflare Queues provider) by default during installation; existing sites must enable it from the plugin management page. Administrators can disable it to stop task submission and scheduling. Backlogged messages delivered after deactivation are subject to the existing retry budget.

After signing in, administrators can open **Manage → Queues** (visible only while the Queue plugin is enabled) to view provider status and near-realtime backlog metrics. The Queue plugin uses the Worker `QUEUE` binding for metrics without API credentials. To also show account-level Queue settings and consumer settings, create a Cloudflare API Token with only the **Queues Read** permission and enter the Cloudflare account ID and API token under **Plugins → Queue → Settings**; they are stored in the site database as plugin configuration, and the token is masked in the form.

Both values are optional; without them the page still shows realtime metrics available from the `QUEUE` binding. This deployment does not configure a dead-letter Queue, so messages that still fail after the retry limit are discarded by Cloudflare. The page does not pull, lease, delete, or replay messages, and it does not record per-task running or completed history.

The first `wrangler deploy` may write a generated `database_id` back into `wrangler.jsonc`. Do not commit that change (`git checkout -- wrangler.jsonc`); later deploys stay bound to the same resources. Only edit `database_name` / `bucket_name` if you want different resource names.

## Command Reference

| Command | Description |
|---------|-------------|
| `pnpm run dev` | Start local dev server |
| `pnpm run build` | Production build |
| `pnpm run deploy` | Local: task Queue preflight + build + deploy (default Wrangler config) |
| `pnpm run deploy:dry-run` | Build and validate Wrangler deploy config without creating Queues |
| `pnpm run deploy:ci` | Workers Builds production deploy (build/resources already prepared) |
| `pnpm run ops` | Operational tooling entry point; lists subcommands |
| `pnpm run ops db generate` | Generate Drizzle migrations |
| `pnpm run ops db studio` | Launch Drizzle Studio |
| `pnpm run ops db migrate` | Migrate PHP Typecho data (`--target local\|cloudflare`, `--dry-run`) |
| `pnpm run ops user reset-password` | Reset user password (`--target local\|cloudflare`) |
| `pnpm run lint` | Type-aware checks for TS, Astro (frontmatter and inline scripts), tests, and scripts |
| `pnpm run typecheck` | Generate Workers / Astro types and run the TypeScript check |
| `pnpm run test` | Run all tests |
| `pnpm run test:watch` | Watch mode |
| `pnpm run test:coverage` | Generate coverage report |

`src/plugins/*` and `src/themes/*` are pnpm workspace packages. The loaders read local extension sources directly, so rerun `pnpm run dev` or `pnpm run build` after editing them. When adding or removing an in-tree extension, update its `workspace:*` dependency in the root `package.json` and run `pnpm install`.

After changing bindings in `wrangler.jsonc`, run `pnpm exec wrangler types worker-configuration.d.ts` (`pnpm run typecheck` also does this). Generated `worker-configuration.d.ts` is for local/CI use only and is not committed.

The example config persists searchable Workers Logs and records traces at about 1% sampling; tune for production traffic and cost. Put secrets via `wrangler secret put` (or `.dev.vars` locally), never in tracked config files.

## Migrating from PHP Typecho

```bash
# Cloudflare (production)
pnpm run ops db migrate --target cloudflare \
  --source /path/to/typecho.db \
  --uploads /path/to/usr/uploads

# Local (development)
pnpm run ops db migrate --target local \
  --source /path/to/typecho.db \
  --uploads /path/to/usr/uploads

# Preview (no writes)
pnpm run ops db migrate --target local --dry-run \
  --source /path/to/typecho.db \
  --uploads /path/to/usr/uploads
```

| Option | Description | Default |
|--------|-------------|---------|
| `--source`, `-s` | Source SQLite database path | (required) |
| `--uploads`, `-u` | Source `usr/uploads/` directory; omit to migrate database data only | (optional) |
| `--prefix` | Source table prefix | `typecho_` |
| `--dry-run`, `-n` | Preview mode | `false` |
| `--site-url` | New site URL (for rewriting attachment URLs) | — |
| `--d1-name` | D1 database name | `typecho-cf-db` |
| `--r2-bucket` | R2 bucket name | `typecho-cf-uploads` |

Password hashing is incompatible (PHP phpass → PBKDF2-SHA256), so reset passwords after migration:

```bash
pnpm run ops user reset-password                     # local
pnpm run ops user reset-password --target cloudflare # Cloudflare
```

## Security & Test Rules

- Admin APIs must use `requireAdminAction()` for authentication, authorization, and CSRF checks; admin redirects must be same-origin and limited to `/admin` paths.
- Comment referer checks and post-comment redirects must trust sources by URL `origin`, not by string prefix or host-only comparison.
- Frontend, admin, plugin route, and cache-hit responses are normalized by middleware with baseline security headers.
- Every feature or bug fix needs matching regression coverage and must pass both `pnpm run test` and `pnpm run typecheck`.
